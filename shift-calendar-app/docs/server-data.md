# 서버 최소 데이터 점검 (회사 서버 D1 · 공유 서버 KV)

[SRV-03] 2026-10-22, 앱 1.22.0(묶음 B) 코드 기준. 두 서버가 가진 **모든 표와 키**를 적고, 왜 있는지, 언제 지우는지, 사람(설치)과 이어지는지를 봤어요. 회사 서버의 `SCHEMA`에 표가 생기면 이 문서에도 줄이 있어야 `server/company-worker/test/server-data.test.mjs`가 통과해요.

처리방침 2.8(`privacy/index.html`)과 유출 대응 절차(`incident-response.md`)가 이 표를 기준으로 해요. 개인정보 보호법 제21조(파기)와 제30조(처리방침)의 근거 표예요.

## 원칙 (SHR-09)

- 서버에는 **이용자가 고른 공유·회사 규칙·광장·문의·구독 확인**에 필요한 것만 둬요. 근무표 원본, 급여 내역과 금액(임금표 시세 빼고), 메모 전체, 이름·전화번호·메일 주소(운영자 계정 빼고)는 서버에 없어요.
- **IP 주소는 저장하지 않아요.** 남용을 막는 키는 IP와 비밀 값(`RATE_SALT`)의 해시이고, 한 시간~하루 뒤 지워요.
- 설치를 가리키는 값은 휴대폰이 만든 무작위 번호의 **해시**(`device`)뿐이에요. 앱의 '이 휴대폰이 보낸 정보 모두 지우기'가 이 해시로 찾은 것을 지워요.
- 지우는 때가 정해진 것은 매시간 도는 `prune`(회사 서버)과 KV 만료(공유 서버)가 지워요.

## 백엔드를 고른 기준 (SHR-10)

Cloudflare Workers + D1 + KV를 골랐어요. Supabase 무료 계획은 1주 동안 쓰지 않으면 프로젝트를 일시 정지하고, Firebase는 무료 일 쓰기 한도와 Google 계정 종속이 있어 이용자가 적은 시기에 서버가 멈출 수 있어서예요. 무료 한도(2026-10-22 Cloudflare 문서): D1 DB 하나 500 MB·하루 읽기 500만 행·쓰기 10만 행, KV 하루 쓰기 1,000번·같은 키 초당 1번, Workers 하루 요청 10만. 1.22의 설계가 이 한도 안에 드는 이유는 `research/1.22-서버법령.md` 6장에 있어요.

## 회사 서버 (`server/company-worker`, D1)

**2.0.0** [RVQ-16] 이 표는 보관 장부 `server/company-worker/src/retention.js`에서 만들어요(손으로 고치지 않아요). 표를 새로 만들면 장부에 한 줄(무엇·왜·지우는 때·설치와 이어짐, 설치 해시 열과 모두 지우기에서 하는 일, 정기 정리, 하루 백업)을 적어야 `test/retention.test.mjs`가 통과하고, 같은 장부에서 모두 지우기의 마지막 쓸기·정기 정리 문장·백업의 빼기와 잠그기가 나와요. 표를 다시 쓰려면 `BAMNAT_WRITE_SERVER_DATA=1 node --test test/retention.test.mjs`.

- **모두 지우기**: 지움 / 연결만 끊음(채택된 규칙·글, 결제·환불 기록) / 법정 기간 남음(구매·동의 기록) / 진행 중인 제재는 끝날 때까지. 시험이 모든 표에 설치 해시를 넣고 모두 지우기를 돌려 앞의 두 가지 말고는 해시가 남지 않는지 봐요.
- **하루 백업**(R2, 14일): 뺌은 곧 지워지거나 다시 만들 수 있는 것, 잠금은 그 칸을 서버 비밀값(`SEAL_KEY`, 없으면 `RATE_SALT`)으로 잠가 R2만 새어서는 열 수 없게 한 것이에요.
  표는 8MB(압축 전)마다 조각(`d1/<날>/<표>.<n>.ndjson.gz`)으로 나눠 쓰고, 매시 작업 한 번에 24MB까지 쓴 뒤 다음 시간에 이어 가요. 끝나면 `manifest.json`(판 2: 표마다 줄 수·조각 수·잠근 칸).
  2.0.0 전의 백업(잠그지 않은 것)은 14일 보관이 지나며 저절로 지워져요.
- **되살리기 연습**(검토 U21-08): 7일마다 매시 작업이 마지막 날을 모두 다시 읽어 줄마다 열리는지, 줄 수가 목록과 같은지, 잠근 칸이 지금 열쇠로 열리는지(표마다 3칸) 보고 오늘 DB 줄 수와 나란히 적어요(관리 › 백업, D1에는 쓰지 않음). 문제가 있으면 관리자 알림.
  실제로 되살릴 때: R2에서 그날 폴더를 내려받아 `BAMNAT_BACKUP_SECRET=<그날 잠근 비밀값> node server/company-worker/tools/backup-open.mjs <폴더> > restore.sql`(잠근 칸이 안 열리거나 조각이 없으면 아무것도 쓰지 않고 멈춰요), 로컬 서버에 먼저 넣어 보고 `npx wrangler d1 execute bamnat-company --remote --file=restore.sql`. 해마다 6월에 손으로 한 번(운영 달력 `backup-restore`). 로컬에서 미리 해 보기: `npm run local -- 8789 --seed --backup local-backup`로 켜고 관리 › 백업 › 지금 이어서 백업 → 되살리기 연습 › 지금 연습하기, 그다음 `BAMNAT_BACKUP_SECRET=local node tools/backup-open.mjs local-backup/d1/<날짜>`(로컬 서버의 R2는 `--backup` 폴더의 파일, 없으면 메모리).
- **데이터 요청 대행**(검토 U21-07·I21b-02): 관리 › 데이터 요청에서 문의에 묶인 요청(또는 그분이 가진 복구 코드)으로 서버에서 '모두 지우기'나 '가진 것 내보내기(JSON)'를 바로 해요. 지운 표·줄 수와 남은 것(요청 문의·법정 기록·진행 중 제재)과 까닭, 내보낸 표·줄 수가 그 요청의 증빙으로 남아요(`data_requests.proof`). 복구 코드는 설치를 찾는 데만 쓰고 저장하지 않아요. 내보내는 파일에는 비밀 칸·사진 같은 큰 칸을 빼고 설치 해시는 '이 설치'로 적어요.
