# 1.30 SP1 개발계획·결과: 서버 조회 속도 (SPD-01~09)

사용자 말(2026-10-27): "여전히 조회하는 로딩이 너무 느리다. 획기적으로 속도를 빠르게 할 방법. 아주 중요한 문제."
설계: `/tmp/claude-0/plan130/R2-조회속도.md` 2장 SP·5장 SP1. 범위: `server/company-worker`의 읽기 함수·GET 분기, 새 모듈 `src/read-fast.js`, 시험. 앱 코드는 고치지 않았어요(AP1 몫).

## 1. 한 줄 결론

규칙 광장(투표 중) 한 쪽을 그리려고 서버가 D1을 **44번 차례로** 기다리던 것을 **2번**으로 줄였어요. 회사 화면 8 → 2, 회사 방 9 → 3, 토론 16 → 2, 내 활동(보낸 것 50개면 100) → 1~2. 답의 모양과 값은 그대로예요(1.29 서버와 같은 DB에서 42개 경로를 물어 JSON이 모두 같음). 여기에 D1 세션(읽기 복제)·Smart Placement·짧은 보관·묶음 응답·전체 회사 목록(ETag)을 더해 앱(AP1)이 "화면 하나 = 요청 하나, 요청 하나 = 왕복 2~3번"으로 갈 수 있게 했어요.

## 3. 한 일

- **SPD-01 묶음 상태 읽기** (`index.js` `readStates`·`representatives`·`stableFacts`·`statesFor`): `state()`가 판 하나에 5문장씩 읽던 것을 (회사, 판) 쌍 N개에 대해 4문장(`reports`+별명, `votes`, `posts` 수, `uses` 수)으로 한 번에. `opinions()`(맞아요·달라요·이유·내 표), `stableOf()`(안정), `representative()`(대표 제보, 창 함수 ROW_NUMBER), `blocker()`(내린 판)도 같은 줄들에서. D1은 문장 하나에 값 100개까지라 `spPairChunks`가 회사+판 90개씩 나눠 같은 왕복에 보내요(시험이 100 넘는 bind를 실패로 잡음).
  - `board()`: 설정과 목록을 함께, 그다음 상태·대표 제보 함께 → 2왕복.
  - `companyData()`(=`company()`): 회사 줄·누가 묻는지·별칭·채택·대기·내린 판·안정 자료를 함께, 그다음 상태·대표·의견 → 2왕복. `markLeads`는 이미 읽은 표로(동기 함수).
  - `roomData()`(=`room()`): 어디·누구 → 목록·내 판·안정 → 상태 = 3왕복.
  - `talkData()`(=`talk()`): 어디·누구·열려 있는지 → 글과 글쓴이에 관한 11가지 → 제안 상태 = 2~3왕복. BC가 고칠 `proposal = { setup: r.grp, ...states.get(key), lines: [] };` 줄은 그대로 두었어요(한 줄 호출을 넣기 쉬움).
- **SPD-02 D1 세션·Smart Placement**: `read-fast.js` `spSession()`이 광장 읽기(`/api/companies…`, `/api/board`, `/api/plazas`, `/api/terms`, `GET /api/members`)와 광장 쓰기(`reports`, `votes`, `posts…`, `uses`, `members`, `nick`)만 `env.DB.withSession()`으로 감싸요. 시작점: 앱이 보낸 `x-d1-bookmark` → 없으면 쓰기·`X-Device` 있는 읽기·`Cache-Control: no-cache`는 `first-primary`, 나머지는 `first-unconstrained`. 답에 `x-d1-bookmark`와 `x-d1-region`(D1 `meta.served_by_region`, 원본이면 `;primary`). Worker 메모들(`schemas`, `meters`, `namesFilled`, `topMemo`, 새 것들)은 `spDbKey(env)`(세션 아래 원래 DB)로 묶어 세션 때문에 메모가 사라지지 않게. 관리자 앱과 나머지 경로는 그대로. `withSession`이 없는 런타임(Node 시험의 옛 모의, 로컬)도 그대로 동작. `wrangler.toml` `[placement] mode = "smart"`.
- **SPD-03 salt·색인**: `salt()`는 Worker마다 한 번 읽고(있으면 쓰지 않음) 메모. 색인 `reports_rule ON reports (rule_id) WHERE rule_id IS NOT NULL`, `posts_report ON posts (report_id) WHERE report_id IS NOT NULL`. `SCHEMA_VERSION`은 표·색인 목록의 해시라 저절로 바뀌어 배포 뒤 첫 요청이 한 번 만들어요.
- **SPD-04 짧은 보관**: `/api/board` 엣지 20초(+swr 120)·Worker 메모 15초, `/api/plazas` 300초(엣지·메모), `/api/terms` 엣지 600초(메모 없음: 관리자가 바꾼 설정이 바로 보이게). 키는 정렬한 쿼리. 이 Worker로 쓰기가 오면 메모를 비우고, 앱이 `Cache-Control: no-cache`를 보내면 엣지·메모를 건너뛰고 새로 읽은 답을 다시 보관해요.
- **SPD-05 `GET /api/companies/:id?with=room,talk`**: 참여자면 페이지에 `room`(=`/room`의 답), `talk`(=`/setups/room/posts`의 답, 최근 100글까지)을 더해요. 방·토론은 페이지의 두 번째 왕복과 나란히 돌아 3왕복. 참여 읽기 횟수(하루 120)는 한 번만 셈. 비참여·제한(`limited`)이면 페이지만. 옛 필드는 그대로.
- **SPD-06 `GET /api/companies/all`**: 숨김·합침·직군 공통을 뺀 모든 회사 `{id, name, aliases[], said, cho, adopted, pending, first?, users, sites, lead}`, `n`, `at`. `lead`는 검색 답과 같은 줄(`searchLeads(env, ids, true)`: IN 없이 표 전체를 한 번에). Worker 메모 5분(no-cache로도 새로 만들지 않음: 가장 무거운 읽기라), 엣지 300초, `ETag`(목록 JSON의 SHA-256 앞 12바이트), `If-None-Match`가 같으면 304(본문 없음). 시간당 공개 읽기 한도(600)에 넣었어요. 회사 하나 약 300~500바이트.
- **SPD-07 왕복 예산 시험** `test/perf-rounds.test.mjs`(19개): 위 표의 예산. 문장마다 25ms, bind 100개 넘으면 실패, 두 번 재서 짧은 쪽.
- **SPD-08 `POST /api/members?with=page`**(또는 본문 `"with": "page"`): 참여 답에 `page`(참여자로 읽은 회사 화면, `GET`과 같은 답). 옛 앱은 안 보내니 답이 그대로. 409(기다림·한도)에는 없음.
- **SPD-09 스스로 찾은 것**: `activity()`가 보낸 제보마다 `score`+`uses`를 차례로 읽어 50개면 100왕복 → 한 번에(2왕복). `rates()` 4 → 1, `plazas()` 3 → 1, `history()` 판마다 2 → 전체 2(상관 서브쿼리). 쓰지 않게 된 `payMark` 삭제.

## 4. 결정 (점검 문서와 달라진 것)

- **R2의 색인 다섯 개 중 셋은 필요 없었어요.** `votes`·`uses`의 기본 키가 `(company_id, grp, device)`라 `company_id, grp`로 이미 찾고, `members`는 `members_company`로 찾아요(EXPLAIN QUERY PLAN으로 확인, 시험에 넣음). 실제로 없던 `reports(rule_id)`·`posts(report_id)`만 더했어요(부분 색인).
- **workers.dev에서는 엣지 캐시(Cache API)가 아무것도 보관하지 않아요**(Cloudflare 문서: 동작하는 cache는 직접 연결한 도메인의 Worker). 지금 서버 주소가 workers.dev라 AS의 검색 엣지 캐시도 실제로는 안 쓰였을 가능성이 커요. 그래서 엣지 캐시에 더해 **Worker 메모리 보관**(광장 15초, plazas 5분, all 5분)을 넣었어요. 사용자 도메인을 연결하면 엣지 캐시도 같이 써요.
- **D1 세션 시작점을 셋으로 나눔**: R2는 bookmark 없으면 `first-unconstrained`였지만, 1.29 앱은 bookmark를 보내지 않으면서 쓰기 직후 자기 표·글을 다시 읽어요. 복제가 켜지면 그 읽기가 늦은 사본에서 나와 "방금 쓴 게 안 보임"이 생길 수 있어, `X-Device`가 있는 읽기·쓰기·`no-cache`는 원본에서 읽게 했어요. 쓰기 답에도 bookmark를 주므로 1.30 앱은 사본에서 읽으면서도 자기 쓰기를 봐요.
- **`/members` page는 `?with=page`일 때만**: 1.29 앱의 참여 답이 느려지지 않게(페이지 계산 2왕복을 옛 앱은 쓰지 않음).
- **약관은 Worker 메모 안 함**: 관리자 설정이 바로 보여야 하고(기존 시험도 그렇게 기대), 앱이 하루 디스크 보관(AP1)하면 충분해요.
- **`/all`의 바이트 예산**: 회사 1,000곳이면 약 400KB(gzip 약 70KB). 304로 대부분 0바이트.

## 6. 다른 묶음과 맞닿는 곳

- **AP1(2차, 앱)**: 쓸 수 있는 서버 계약
  - `GET /api/companies/{id}?with=room,talk` → 기존 필드 + `room?`, `talk?`(참여자일 때만). 없으면(옛 서버, 비참여) 따로 부르면 돼요. `CompanyApi.companyBundle(id, device)`가 이걸 쓰면 돼요.
  - `GET /api/companies/all` → `ETag`를 저장하고 다음에 `If-None-Match`로 보내면 304. `said`·`cho`가 들어 있어 앱 `CompanyMatch`로 바로 찾을 수 있어요(별칭의 읽기는 앱이 `spoken`으로 만들기).
  - `POST /api/members?with=page` → 답의 `page`가 그 회사 화면(참여자 시점). `PayFind.kt`(BA 소유)에서 쓰려면 join 요청 URL에 `?with=page`를 붙이고 `o.optJSONObject("page")`를 회사 화면 파서에 넘기면 돼요.
  - 쓰기 뒤 같은 목록을 다시 읽을 때 `Cache-Control: no-cache` 머리글. 모든 답의 `x-d1-bookmark`를 기억했다가 다음 GET에 `x-d1-bookmark`로 보내기(값은 그대로, 기기 정보 아님).
- **BC**: `talk()` 본문이 `talkData()`로 옮겨졌어요. 제안 줄 `proposal = { setup: r.grp, ...states.get(key), lines: [] };`은 그대로라 같은 자리에 한 줄을 넣으면 돼요.
- **AX(관리자)**: `statesFor(env, [{company, grp, adopted}], threshold)`(Map, 키 `company\u0001grp`)와 `readStates`·`representatives`·`stableFacts`를 export해 두었어요. 관리자의 `같은 회사 여러 판`·`companyInfo`(`stableOf`를 판마다 부름)도 이걸로 바꾸면 같이 빨라져요(관리자 라우트는 건드리지 않았어요).
- **BD(2차)**: `company()`의 호출 줄을 넣는다면 `companyData()` 안이에요.
- 통합: `SCHEMA_VERSION`은 해시라 다른 묶음이 색인을 더해도 충돌 없이 한 번에 바뀌어요. `LATE_INDEXES` 끝에 `// SP1 1.30` 블록이 있어요.

## 7. 사용자가 할 일 (Cloudflare 대시보드, README 5-3에도 있음)

서버 코드를 다시 붙여 넣고 배포(README 3번)한 다음:

1. **D1 위치 보기**: 왼쪽 메뉴 **저장소 및 데이터베이스(Storage & databases) → D1 SQL 데이터베이스 → `bamnat-company` → 지표(Metrics)**에서 쿼리를 처리한 지역(Region)을 봐요. APAC(아시아·태평양)이 아니면 멀리 있는 거예요. 위치는 만든 뒤 바꿀 수 없어서 2·3번이 그 거리를 메워요. 배포 뒤 아래 확인의 `x-d1-region`으로도 보여요.
2. **Smart Placement 켜기**: **컴퓨팅(Workers) → Workers 및 Pages → `bamnat-company` → 설정(Settings) → 일반(General) → 배치(Placement) → 스마트(Smart)** 고르고 저장. 15분쯤 뒤부터 효과.
3. **읽기 복제 켜기**: **저장소 및 데이터베이스 → D1 SQL 데이터베이스 → `bamnat-company` → 설정(Settings) → 읽기 복제 켜기(Enable Read Replication)**. 추가 요금 없음(읽은 행·쓴 행 그대로).
4. **RATE_SALT 확인**: **Worker `bamnat-company` → 설정(Settings) → 변수 및 비밀(Variables and Secrets)**에 `RATE_SALT`(Secret)가 있는지. 없으면 README 5번대로 넣고 배포.
5. **확인**: `https://bamnat-company.<계정 이름>.workers.dev/api/board?tab=voting`을 컴퓨터에서 `curl -sI`로 열어 `x-d1-region`, `cf-placement`(`remote-…`면 옮겨짐)를 보고, `curl -s -o /dev/null -w '%{time_starttransfer}\n' <주소>`를 열 번 돌려 시간을 봐요. (선택) 직접 도메인을 연결하면 `cf-cache-status`로 엣지 보관도 보여요.

## 8. 처리방침·데이터·권한 영향

- **새로 수집하는 값 없음.** `x-d1-bookmark`는 D1이 만든 세션 토큰(데이터베이스 시점)이고 기기·사람과 무관. `x-d1-region`은 서버가 답한 지역. `/api/companies/all`은 `/top`·검색과 같은 공개 정보(이름·다른 이름·읽기·숫자), 기기·금액 없음(시험으로 확인).
- D1: 색인 2개 추가만(열·표 추가 없음). Room DB·앱 권한 영향 없음.
- 보관: Worker 메모리에 공개 목록을 15초~5분. 쓰기 경로의 개인 데이터는 보관하지 않아요.

## 9. 남은 것

- 실제 운영 D1의 지역·복제·Smart Placement 효과는 배포 뒤 사용자 확인이 필요해요(Claude는 Cloudflare 토큰이 없음).
- 관리자 라우트의 판마다 읽기(`companyInfo`의 `stableOf`, `queue` 등)는 AX 소유라 그대로예요. `statesFor`를 쓰면 같이 빨라져요.
- 첫 검색 직후 `fillNames`의 일괄 쓰기(쓰기 직후 한 번)는 R2 측정에서 17왕복으로 보였지만, 측정 래퍼가 batch 안의 문장을 하나씩 기다린 탓이고 실제 D1에서는 batch 한 번이에요. 바꾸지 않았어요.
- 엣지 캐시는 workers.dev에서 동작하지 않아요. 더 빠르게 하려면 사용자 도메인 연결(선택)을 다음 판에서 검토.
