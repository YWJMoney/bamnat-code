# 1.29 AS 회사 검색 속도·광장 대표판 검색·데이터 로딩 속도

추적표 접두사 `SRCH-` (SRCH-01 ~ SRCH-14). 사진 1280 ~ 1286.

## 사용자 요청 (2026-10-27)

- "광장에 대표판이 있는데 회사 검색 시 뜨지 않고 있다"
- "안 뜨는 게 아니라 늦게 떠서 안 뜨는 것처럼 보이는 거다. 빠르게 뜨게 하는 방법을 고민하고 적용해야 한다"
- "데이터 검색에 관한 모든 로딩이 너무 느려서 처음 사용하는 사용자가 불편함을 많이 느끼고 있다"

## 원인 (찾은 것)

1. 서버가 검색 결과 중 처음 5곳에만 대표 주기를 붙였고, 그것도 한 곳씩 차례로 읽었다(검색 한 번에 읽기 41~56번). 6번째 아래 회사는 대표판이 있어도 대표 주기가 없었다.
2. 앱의 치는 대로 찾기가 2.5초 안에 오지 않은 답을 버렸다. 게다가 `withTimeoutOrNull`이 막힌 `HttpURLConnection` 읽기를 끊지 못해, 버리는 것조차 답이 올 때까지 기다렸다.
3. 회사 찾기 화면의 `collectLatest`가 앞 검색의 막힌 요청이 끝나기를 기다린 뒤에야 다음 글자를 찾았다.
4. 회사 찾기 화면 줄(CompanyRow)은 대표 주기를 아예 보이지 않고 "쓰는 설정 n개"만 보였다.
5. 앱은 GS를 지에스로도 찾아 보지만 서버는 한글 읽기로 된 이름을 찾지 못했다.
6. 처음 사용자는 앱에 아무 검색 결과도 없어서 모든 글자가 서버를 기다렸다.

## 한 일

### 서버 (`server/company-worker/src/index.js`, `// AS 1.29` 묶음, 커밋 8cefd82e)

- `searchLeads(env, ids)`: 결과 전부(최대 20곳)의 대표 주기를 5번의 읽기로 한꺼번에(`IN (...)`, `Promise.all`). [SRCH-01]
- `spoken()`과 `companies.said`, `aliases.said` 칸(기본값 `''`, 열 추가만): 지에스칼텍스로 GS칼텍스를 찾음. 기존 줄은 `fillNames`가 채움. [SRCH-02]
- 검색 응답 `Cache-Control: public, max-age=30, stale-while-revalidate=300`, Cloudflare `caches.default` 엣지 복사본(키는 정리한 이름). [SRCH-03]
- 새 `GET /api/companies/top?n=`: 많이 쓰는 회사 최대 60곳과 대표 주기(숨김·합침·주제 제외, 10분 메모, 엣지 600초). [SRCH-04]
- 회사 화면(`company()`), `state()`, `score()`, `markLeads` 읽기를 동시에. [SRCH-05]
- 응답 바꿈은 더하기만: 1.28 이하 앱은 그대로 동작(전에 없던 6번째 아래 회사의 `lead`가 생길 뿐).

### 앱

- `company/CompanySearch.kt`(새): 모든 회사 검색의 한 길. [SRCH-06][SRCH-07][SRCH-09][SRCH-10]
  - `peek(q)`: 기다리지 않고 지난 답, 앞 글자 답에서 아직 맞는 곳, 미리 받은 많이 쓰는 회사(초성·한 글자 오타·한글 읽기 포함).
  - `states(q)`: 그것을 바로, 잠깐 멈춤(300ms) 뒤 서버, 2.5초 넘으면 "연결이 느려 조금 오래 걸려요", 답은 25초까지 오면 보임.
  - 같은 이름 검색은 요청 한 번. 20초 안의 답은 다시 묻지 않음.
  - `cacheDir/company_search.json`에 많이 쓰는 회사와 최근 답 30개 보관(공개 회사 이름·대표 주기·검색어 키만).
  - `warm()`: 첫 달 뒤(startLater 3묶음, 이름 없는 launch라 예산 21/7 그대로) 12시간마다 많이 쓰는 회사, 내 회사 화면. 절전·데이터 절약이면 안 함.
- `CompanyClient`: 읽기 요청을 따로 된 범위에서(`readCall`), 화면이 기다림을 멈추면 바로 돌아옴. `popular()` 추가.
- 치는 대로 찾기(`CompanyInlineResults`)와 회사 찾기(`CompanyFindViewModel`)가 `states`를 씀. 찾는 단계 줄 `SearchStageLine`, 자리 표시 `SkeletonRow`. [SRCH-10][SRCH-11]
- 회사 찾기 줄에 대표 주기와 믿음 줄(n명 쓰고 있어요 · 맞아요 n명 · 급여 방식 있음). [SRCH-01]
- 공개 자료 검색 색인 미리 계산(`PublicCycles` Entry, `CompanyMatch.Name/Query`). [SRCH-12]
- 로딩 점검 [SRCH-13]: 광장 첫 화면 두 읽기 동시, 회사 화면 캐시 먼저 보이고 새로 고침, 대표판 첫 쪽 캐시와 대표판 탭 미리 읽기, 메모·잠 화면이 공유 `live` 흐름 사용.
  - 그대로 둔 것: 가계부 검색(기기 안, 입력이 바뀔 때만 계산), 설정·도움말 검색(메모리 색인), 공휴일(기기 안), 원격 파일(AO가 처리). 투자 종목 검색은 앱에 없음.

## 결정

- AS-D1: 서버 답을 버리지 않는다. 늦으면 "조금 오래 걸려요"라고 말하고 오면 보인다(25초에서 포기).
- AS-D2: 처음 사용자를 위해 많이 쓰는 회사 목록을 첫 달 뒤 받아 둔다(공개 정보만, 12시간마다).
- AS-D3: keep-alive 손보기(SRCH-08)는 하지 않음. 1.28 코드도 JVM에서 연결을 다시 쓰는 것을 측정함(요청 5번에 연결 1개).
- AS-D4: 새 권한 없음. `ACCESS_NETWORK_STATE`가 없으므로 데이터 요금 연결 여부는 읽을 수 있을 때만 보고, 절전과 데이터 절약(Data Saver)은 항상 지킨다.
- AS-D5: Room 21 그대로. 앱 캐시는 cacheDir 파일 하나(지워져도 다시 받음).

## 개인정보·서버로 보내는 것

- 새로 보내는 개인 정보 없음. 검색어는 전부터 보냈다. 새 `/api/companies/top` 요청은 아무 값도 보내지 않는다.
- 기기에 남는 것: `cacheDir/company_search.json`(공개 회사 이름·대표 주기·최근 검색어 키). 기기 ID·금액 없음.

## 남은 일과 사용자가 할 일

- 사용자: 회사 서버 배포(`wrangler deploy`). 배포 전에는 앱이 `/api/companies/top`을 404로 받아 빈 목록으로 지내고 나머지는 그대로 빨라진다. 첫 요청 때 `said` 칸이 열 추가로 생긴다.
- AP·통합: 급여 '우리 회사 급여 방식 찾기'(PayFindSheet)는 `withTimeoutOrNull(INLINE_WAIT_MS) { inlineSearch(c, q) }` 꼴이라 늦으면 "급여 방식이 없어요"로 보인다. `c.companySearch.states(q)`(Flow<CompanySearch.State>, stage ASKING/SLOW/DONE/FAILED)나 `SearchStageLine(state, nothingYet)`을 쓰면 늦은 답도 보인다. 고치지 않아도 `inlineSearch(c, q)`는 공개 시그니처 그대로 더 빨라졌다(20초 안 답은 바로, 같은 검색 한 번, 2.2초에 아는 회사로 대신).
- 실제 휴대폰·망에서의 측정은 하지 않았다.
