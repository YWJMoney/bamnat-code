# 디자인 품질 조건 (2.0.0부터 모든 작업의 통과 기준)

> **사용자(2026-11-12 13:24 KST)**: "너는 모든 작업에 있어 디자인 품질을 가장 중요하게 봐야해 개발 내용도 중요하지만 사용자들이 보는 디자인이 기본으로 최정상급이고 동작하기가 편해야 기능의 성능이 진정 빛을 바랠수 있어 개발을 진행하면서 품질 조건을 꼭 확인해는것을 기본으로 해야해"

화면에 닿는 모든 고침·새 기능은 아래 조건을 **만들기 전에 읽고, PR 전에 스스로 확인하고, 합치기 전에 총괄이 화면 사진으로 다시 확인하고, 통합 빌드에서 PC가 손으로 확인**해요. 기능이 되는 것만으로는 끝난 것이 아니에요. 조건에 못 미치면 합치지 않고 돌려보내요.

근거: 검토 보고서 5장(디자인은 지금이 최선인가), `영역/13-공통UI-디자인-성능-접근성.md`의 '디자인 총평', 사용자 결정 17번(5장 추천대로 앱 전체), 개발 지시서 4-4·4-5(도약 숫자 26~39번), 저장소 `CLAUDE.md` 3항(스크롤·오가기 점검, 실제 사용자처럼 끝까지 쓰기).

## 1. 조건 16가지

### 가. 첫눈에 (화면을 짜는 법)
1. **핵심이 먼저 보여요.** 그 화면의 주인공(달력, 금액, 목록의 첫 줄)이 스크롤 없이 화면 위 25% 안에서 시작해요. 달력 위는 한 줄(높이 56dp 띠 하나 + 알림함 숫자)이에요.
2. **채운 단추는 화면에 하나.** 지금 할 일 하나만 채우고, 글자 단추는 2개까지, 나머지는 '더 보기'로 보내요. 같은 무게의 단추가 줄지어 있으면 통과하지 못해요.
3. **안내 카드는 한 모양.** 바탕 한 가지, 왼쪽 아이콘 색으로만 뜻(안내·주의), 누를 단추 하나, X 하나. 답한 뒤에는 접히거나 한 줄 요약으로 남아요.
4. **글은 짧고 읽히게.** 설명은 한 줄 요약과 ⓘ. 12sp 이하는 보조 정보에만, 8~9sp는 쓰지 않아요. 한 화면이 문서처럼 읽히면 통과하지 못해요.

### 나. 한결같게 (값과 부품)
5. **색·모서리·간격·움직임은 공통 값만.** 직접 적은 값은 0(막대·점 같은 예외는 목록에). 공통 부품(시트·작은 창·카드·칩·빈 화면·큰 숫자·뼈대 줄)이 있으면 새로 만들지 않아요.
6. **의미색을 아껴요.** 빨강은 위험만, 주황은 주의만. 한 화면에 빨강이 여러 번 나오면 통과하지 못해요.
7. **상태가 한결같아요.** 빈 화면은 빈 화면 부품(캐릭터 + 한 줄 + 단추 하나), 기다릴 때 목록은 뼈대 줄, 인터넷 없음은 세 문구(연결 없음·서버 바쁨·시간 넘김), 저장·실패는 말로 알려 줘요.

### 다. 쓰기 편하게 (동작)
8. **가장 흔한 일은 2번 안에.** 그 화면에서 가장 자주 하는 일의 누르는 횟수를 앞뒤로 세어 PR에 적어요. 늘어나면 통과하지 못해요.
9. **손에 맞아요.** 누르는 곳은 48dp(작아도 44dp), 떠 있는 단추가 글·카드를 가리지 않고, 맨 아래 카드가 아래 막대에 가리지 않아요. 보이는 닫기가 없는 창은 없어요.
10. **적던 것은 사라지지 않아요.** 화면이 다시 만들어지거나 앱이 뒤로 가도 남고, 닫기·뒤로·바깥 누르기 전에 한 번 물어요. 되돌리기는 약속한 대로 뜨고 그것이 바꾼 것만 되돌려요.
11. **스크롤과 오가기가 매끄러워요.** 끝까지 내리고·튕기고·다시 올리고·반쯤 내린 채 다른 탭에 다녀와도 튀거나 잘리지 않고, 스크롤 위치와 고른 칩이 그대로예요.

### 라. 누구에게나
12. **어떤 화면에서도 안 깨져요.** 어두운 모드, 밤 색, 글자 150%·200%, 폴드 접은 폭(약 380dp)과 편 폭(673dp 이상)에서 잘림·겹침·세로로 선 글자가 없어요. 금액은 줄이지 말고 줄을 바꾸거나 한 단계 낮춰요. 넓은 화면에서 본문은 최대 640dp, 표는 가득이에요.
13. **그 사람의 말로.** 교대·일근·알바·현장·가게·투자·사장님·팀 리더·직원 각각에 맞는 낱말만 보여요(유형 낱말 검사 시험 0건). 맞지 않는 기능은 숨겨요.
14. **접근성.** 읽어 주는 이름(contentDescription), 색만으로 뜻을 전하지 않기, 글자와 바탕의 대비.

### 마. 느낌
15. **움직임이 가볍고 한결같아요.** 공통 길이만 쓰고 시스템 '움직임 줄이기'를 따르며, 느린 프레임은 5% 아래예요.
16. **따뜻해요.** 빈 화면·처음 만나는 화면·끝낸 순간에 캐릭터 '말랑 칸이'와 사람 말투의 한 줄이 있어요. 겁주는 말, 기계 말투, 탓하는 말이 없어요.

## 2. 확인하는 법 (네 번)

| 언제 | 누가 | 무엇을 |
|---|---|---|
| 만들기 전 | 갈래 | 이 문서와 갈래 P의 공통 부품 문서를 읽고, 바꿀 화면의 '지금' 사진을 찍어 둬요(화면 사진 시험 또는 9차 사진) |
| PR 전 | 갈래 | 바뀐 화면마다 화면 사진 시험으로 **밝은·어두운 × 글자 100%·200% × 접은 폭·편 폭**(해당하는 것)을 찍고, 아래 '품질 표'를 PR 본문에 넣어요. 사진은 프로젝트 파일 `계획/2.0.0-화면사진/<갈래>/<PR 번호>/`에 앞·뒤를 나란히 둔 모음 사진(JPEG, 장당 400KB 안, PR당 12장 안)으로 올려요 |
| 합치기 전 | 총괄 | 모음 사진을 직접 열어 조건 16가지를 봐요. 못 미치면 고칠 곳을 적어 돌려보내요. 세는 시험(갈래 P가 만드는 달력 시작 높이·채운 단추 수·공통 값 밖 모서리와 여백)이 CI에서 지켜요 |
| 통합 빌드 | PC 검증 스레드(Fable, 사용자 11-12 13:30) | 에뮬레이터에서 손으로: 스크롤·오가기, 누르는 횟수, 큰 글자, 폴드, 유형 아홉 가지 둘러보기. 결과 파일에 '디자인 품질' 절(조건 번호별로 못 미친 화면·사진) |

**검증 단계도 검토예요**(사용자 2026-11-12 13:30 KST: "실제 에뮬레이터로 검증하는 스레드는 Fable로 열어서 검증 확인단계에서도 피드백과 빈틈을 찾게"). PC 검증 스레드는 확인 목록의 줄만 통과시키지 않고, 지나가는 모든 화면을 위 16가지로 보고 못 미친 것·더 편할 방법·유형에 맞지 않는 것·목록에 없는 새 문제를 적어요. '되기는 하지만 불편한 것'은 통과가 아니라 '됨(다듬을 것 있음)'이에요. 결과는 총괄이 추적표의 새 줄로 넣어 맡은 갈래에 돌려줘요.

### PR 본문에 넣는 '품질 표'

```
## 디자인 품질 (조건 16가지)
| 조건 | 결과 | 근거(사진·시험·숫자) |
|---|---|---|
| 1 핵심이 먼저 | 통과 / 못 미침(까닭) / 해당 없음 | 달력 시작 57% → 24% (사진 01) |
| 2 채운 단추 하나 | … | … |
…(16줄 모두)
```

- '못 미침'이 한 줄이라도 있으면 까닭과 언제 고칠지를 적어요. 총괄이 합칠지 정해요. 조건 1·2·8·10·12는 '못 미침'으로는 합치지 않아요.
- 서버·시험만 고친 PR은 '화면에 닿지 않음' 한 줄이면 돼요. 관리자 앱과 공개 웹은 화면이 있으니 같은 조건을 봐요(폭 380·840·1440, 밝은·어두운).
- 공통 부품이 아직 없어서 못 지킨 조건은 '갈래 P 부품 대기'라고 적고, P의 부품이 나오면 그 갈래가 다시 고쳐요(추적표에 줄을 남겨요).

## 3. 세는 시험 (사람이 눈으로 지키지 않게)

갈래 P가 만들고 CI가 돌려요. 숫자는 줄어드는 쪽으로만 가요.

- 달력 탭에서 달력이 시작하는 높이(유형마다) 25% 안
- 화면마다 채운 단추 수 1개 이하
- 공통 값 밖 모서리 0곳, 공통 값 밖 여백 수(늘어나면 실패)
- 8~9sp 글자 0곳, 44dp보다 작은 누르는 곳 0곳
- 유형 낱말 검사(갈래 H)
