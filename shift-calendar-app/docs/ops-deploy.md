# 서버 배포 쓰는 법 (deploy-server)

서버 두 곳(회사 `api.bamnat.app`, 공유 `s.bamnat.app`)은 GitHub Actions `deploy-server`로 올려요. 사용자 결정(2026-11-08)으로 Claude가
시작해 끝까지 해요(승인 단계 없음). 안전장치와 순서의 정본은 `tools/deploy_worker.py` 맨 위 설명이고, 이 문서는 쓰는 사람이 볼 것만 모았어요.

## 누가

- 2.0.0 동안 회사 서버는 갈래 D가 통합 브랜치(`claude/project-thread-f33c16`)에서만 올려요. main에서 회사 서버를 올리지 않아요(RVD-19 전까지).
- 다른 갈래는 배포하지 않고, 서버를 고친 PR이 합쳐지면 D(또는 총괄)에게 알려요.

## 차례

1. Actions › deploy-server › Run workflow를 **main에서** 눌러요(다른 브랜치에서 누르면 gate가 멈춰요).
2. `ref`에 배포할 브랜치, `target`(both·company·share), `mode: check`로 먼저 돌려요. check는 새 판을 올리고 바인딩을 대조하는 데까지만이라
   손님은 앞 판 그대로예요.
3. 요약이 맞으면 같은 값으로 `mode: deploy`. 회사 서버는 10% 카나리 10분 → 100% → health 5번, 하나라도 어긋나면 앞 판·정기 작업까지 되돌려요.
4. 끝나면 사용자에게 한 줄: 판, 배포 번호, 되돌릴 판(그리고 넘긴 시험이 있으면 그것도, 아래).

## 시험에서 멈췄을 때 (2.0.0 RVR-25, 검토 U60-02)

build가 서버 시험에서 멈추면 요약 맨 위에 실패한 시험 이름·줄이 나오고, `explain` 일이 **어제 main의 날짜 시험**(`date-watch.yml`, 매일 06:17 KST)
결과와 견줘 한 줄씩 알려요.

| explain이 말하는 것 | 뜻 | 할 일 |
|---|---|---|
| 어제 main에서도 깨짐 | 이 브랜치 탓이 아니에요(날짜·바깥) | 고치는 PR을 먼저. 급하면 아래 '시험 넘기기' |
| 어제 main에서는 통과 | 이 브랜치의 바뀜 때문일 수 있어요 | 그 바뀜을 먼저 봐요. 넘기지 않아요 |
| 어제 main에 없음 | 새 시험이에요 | 이 브랜치에서 고쳐요 |
| 어제 main 결과 없음 | 날짜 시험 결과를 못 받았어요 | 로그를 보고 판단해요 |

## 시험 넘기기 (`skip_tests`, 2.0.0 RVR-17)

날짜에 묶여 낡은 시험 하나가 급한 고침(보안 등)을 막지 않게 하는 길이에요. **쓰는 규칙**(총괄 2026-11-12):

1. **날짜에 묶여 낡은 시험에만** 써요. explain이 '어제 main에서도 깨짐'이라고 한 시험이 그 예예요. 이 브랜치가 깬 시험은 넘기지 않아요.
2. **그 배포에 대해 사용자가 고르기 카드로 허락했을 때만** 써요. 갈래 스레드가 스스로 넣지 않아요. 카드에는 시험 이름, 왜 깨졌는지, 언제까지 고칠지를 적어요.
3. 값은 `시험 이름|까닭|기한 YYYY-MM-DD`이고 여러 개는 `;`로 이어요. 까닭이 없거나 기한이 지났거나 14일보다 멀면 build가 멈춰요.
4. 넘긴 시험은 build 요약과 배포 기록(notes.txt)에 남아요. **사용자에게 알리는 배포 결과 한 줄에도 넘긴 시험·까닭·기한을 함께** 적어요.
5. 기한 안에 그 시험을 고치는 PR을 따로 열어요.
